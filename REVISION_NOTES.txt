  PART 0 — WHY CAN'T I JUST RUN `python terminal_app.py`?
  (Most Common First-Run Problem — UNDERSTAND THIS FOR VIVA)
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

  THE ERROR YOU MIGHT SEE:
    ModuleNotFoundError: No module named 'mysql'

  WHY DOES THIS HAPPEN?
    mysql-connector-python is NOT part of Python's built-in standard
    library. It is a third-party package that must be installed.
    When you type `python terminal_app.py`, Python uses the SYSTEM
    Python installation, which only has the standard built-in modules.
    The MySQL connector is installed inside the `venv/` folder, NOT
    in the system Python. So the system Python cannot find it.

  WHAT IS A VIRTUAL ENVIRONMENT (venv)?
    A venv is a self-contained copy of Python in a local folder.
    It has its OWN pip and its OWN installed packages, completely
    separate from the system Python. This prevents conflicts between
    projects that need different library versions.
    Our project's venv lives at:  Class-Project/venv/

  THE FIX (Archcraft / Arch Linux):
    OPTION A — Use the run script (easiest, no typing required):
      ./run_terminal.sh
    OPTION B — Activate the venv manually FIRST, then run:
      source venv/bin/activate
      python terminal_app.py
    After running `source venv/bin/activate`, your terminal prompt
    changes to: (venv) user@machine:...$ — this means venv is active.

  THE FIX (Windows):
    OPTION A — Double-click run_terminal.bat (easiest)
    OPTION B — Activate the venv manually in Command Prompt:
      venv\Scripts\activate
      python terminal_app.py

  VIVA TIP: "mysql-connector-python is a third-party library. Because
  Arch Linux uses an externally-managed Python installation, all extra
  packages must be installed inside a virtual environment using pip.
  We activate the venv using `source venv/bin/activate` so Python
  can find the installed mysql.connector module."

  WHY THE SCRIPTS FIX IT AUTOMATICALLY:
    run_terminal.sh and run_terminal.bat both check if the venv
    exists and if mysql.connector is installed. If either is missing,
    they create the venv and run pip install automatically, then
    launch the app using venv/bin/python (Linux) or
    venv\Scripts\python.exe (Windows) directly — bypassing system Python.

  PART A — THE FOUR MAGIC LINES (appear in EVERY function)
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

  LINE 1 →  conn = get_connection()
  WHAT HAPPENS:
    • Python calls get_connection() from db_config.py.
    • The connector library opens a connection to MySQL/MariaDB.
    • MySQL authenticates the username + password.
    • MySQL selects the LabInventory database automatically.
    • A "connection object" (conn) is returned and stored in memory.
  VIVA TIP: Without this line, NO query can reach MySQL at all.

  LINE 2 →  cursor = conn.cursor()
  WHAT HAPPENS:
    • A "cursor" is created INSIDE the already-open connection.
    • Think of conn as a telephone line and cursor as the person speaking.
    • The cursor is the object that actually sends SQL text to MySQL.
    • One connection can have multiple cursors (we use one at a time).
  VIVA TIP: cursor is NOT a database object — it lives in Python RAM.

  LINE 3 →  cursor.close()
  WHAT HAPPENS:
    • Discards the cursor object and releases server-side statement memory.
    • The underlying connection (conn) is still open at this point.
  VIVA TIP: Always close the cursor before closing the connection.

  LINE 4 →  conn.close()
  WHAT HAPPENS:
    • Closes the connection socket to MySQL.
    • MySQL server terminates the session and frees associated buffers.
    • After this line, conn cannot be reused without reconnecting.
  VIVA TIP: If you skip conn.close(), the connection stays open (resource leak).

  PART B — DATABASE CONFIGURATION & CROSS-PLATFORM COMPATIBILITY
  (db_config.py)
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

  1. WHY HAVE A SEPARATE db_config.py?
     • Modularity: Keeps database credentials in one central file.
       If the database password or port changes, you edit ONLY
       db_config.py instead of searching through every file.
     • Separation of Concerns: Interface logic (terminal or GUI)
       remains clean and focused on user interaction, while database
       connection mechanics are handled in one place.

  2. THE DB_CONFIG DICTIONARY:
     DB_CONFIG = {
         "host": "localhost",
         "user": "root",
         "password": ""
     }
     • School Lab (Windows): Usually user="root" and password="" (empty).
     • Home (Linux/Windows): Change password="" to your custom password.

  3. HOW CROSS-PLATFORM CONNECTION WORKS:
     • Windows: MySQL connects over standard TCP port 3306 using
       the host, user, and password from DB_CONFIG.
     • Archcraft / Arch Linux: MariaDB frequently uses unix_socket
       authentication for local users. If standard TCP fails, our
       get_connection() automatically catches the exception and falls
       back to connecting via the local socket file (/run/mysqld/mysqld.sock)
       using the current logged-in Linux username.
     • Result: The project runs out-of-the-box on both Linux and Windows
       without requiring manual code changes!

  PART C — AUTO-INITIALIZING DATABASE (initialize_database())
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

  WHAT PROBLEM DOES IT SOLVE?
    When running a project on a school lab computer or a fresh PC,
    the application usually crashes with "Database does not exist" or
    "Table does not exist" unless someone manually opens a MySQL terminal
    and runs setup.sql.
    initialize_database() fixes this completely!

  HOW IT WORKS (STEP-BY-STEP):
    1. get_connection(database=None) connects to the MySQL server
       WITHOUT specifying a database name.
    2. cursor.execute("CREATE DATABASE IF NOT EXISTS LabInventory")
       creates the database if it doesn't already exist.
    3. cursor.execute("USE LabInventory") switches the session context
       to the LabInventory database.
    4. cursor.execute("CREATE TABLE IF NOT EXISTS Items (...)")
       creates the master inventory table if missing.
    5. cursor.execute("CREATE TABLE IF NOT EXISTS Transactions (...)")
       creates the transaction audit log table with a Foreign Key.
    6. conn.commit() ensures table definitions are permanently stored.
    7. cursor.close() and conn.close() cleanly release resources.

  VIVA TIP: "Both terminal_app.py and gui_app.py call initialize_database()
  immediately on startup. This guarantees zero-setup execution on any
  examiner's machine."

  PART D — cursor.execute() EXPLAINED (%s vs SQL INJECTION)
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

  SYNTAX: cursor.execute(sql_string, values_tuple)

  STEP 1 — Python hands the SQL string template to the cursor.
            The string uses %s placeholders:
            "INSERT INTO Items (name, total_qty) VALUES (%s, %s)"

  STEP 2 — The cursor takes the values tuple (e.g. ("Beaker 250ml", 50))
            and securely formats the data for MySQL.
            It wraps strings in quotes and escapes dangerous characters.

  STEP 3 — The parsed query is sent to MySQL for execution.

  WHY %s AND NEVER f-strings / STRING CONCATENATION?
    If we used: f"INSERT INTO Items VALUES ('{name}', {qty})"
    A malicious user could type:
      Test Item'); DROP TABLE Items; --
    This would cause MySQL to delete the entire table!
    Using %s sends the query structure and user data separately,
    making SQL Injection impossible.

  PART E — CREATE (INSERT) : add_item()
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

  OPERATION: Insert a new lab apparatus or chemical into Items.

  DATA FLOW:
    User Input → Validation → get_connection() → cursor.execute(INSERT)
    → MySQL writes to buffer → conn.commit() writes to disk.

  SQL STATEMENT:
    INSERT INTO Items (name, total_qty) VALUES (%s, %s)

  ROLE OF conn.commit():
    • MySQL operates under transaction control.
    • Changes are held in an in-memory buffer until committed.
    • commit() tells MySQL to flush the buffer and save permanently.
    • If an unhandled exception or crash occurs before commit(),
      MySQL automatically rolls back, preserving data integrity.

  PART F — READ (SELECT) : view_inventory() & FETCHING DATA
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

  OPERATION: Retrieve and display all rows from Items table.

  SQL STATEMENT:
    SELECT item_id, name, total_qty FROM Items ORDER BY item_id ASC

  PYTHON DATA FETCHING:
    • cursor.fetchone():
      Returns the next matching row as a single tuple (e.g. (1, "Beaker", 50)).
      Returns None if no rows match or no more rows remain.
    • cursor.fetchall():
      Returns ALL matching rows at once as a Python list of tuples.
      Example: [(1, "Beaker", 50), (2, "Test Tube", 120)]
      Returns an empty list [] if no rows match.

  VIVA TIP: "After calling cursor.execute() with a SELECT query,
  the result set lives in the MySQL cursor buffer until retrieved
  using fetchone() or fetchall()."


━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
  PART G — UPDATE : issue_item() & restock_item() & ATOMICITY
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

  OPERATION: Modify total_qty and simultaneously record an audit row.

  SQL STATEMENTS (issue):
    1. SELECT name, total_qty FROM Items WHERE item_id = %s
    2. UPDATE Items SET total_qty = total_qty - %s WHERE item_id = %s
    3. INSERT INTO Transactions (item_id, date, qty_change, purpose)
       VALUES (%s, %s, %s, %s)

  WHAT IS ATOMICITY (ACID PROPERTIES)?
    • In issue_item() and restock_item(), TWO database modifications occur:
      an UPDATE on Items and an INSERT on Transactions.
    • Both execute() statements are called within the same connection.
    • Exactly ONE conn.commit() is called after both succeed.
    • If the script crashes after the UPDATE but before the INSERT,
      NEITHER change is saved.
    • This ensures stock numbers never change without an audit trail.

  PART H — FILTERED READ : check_low_stock()
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

  OPERATION: Find items whose stock is at or below a user threshold.

  SQL STATEMENT:
    SELECT item_id, name, total_qty FROM Items
    WHERE total_qty <= %s ORDER BY total_qty ASC

  WHY FILTER IN SQL INSTEAD OF PYTHON?
    • If we fetch all 5,000 items into Python and use an `if qty <= 10:`,
      all 5,000 rows must travel over the network.
    • By putting `WHERE total_qty <= %s` in MySQL, the database engine
      uses indexed filtering and sends only the 3 matching rows.
    • This reduces memory consumption and network latency.

  PART I — JOIN READ : view_transactions() & FOREIGN KEYS
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

  OPERATION: Combine Transactions and Items tables to display
             human-readable names instead of raw item_id numbers.

  SQL STATEMENT:
    SELECT t.trans_id,
           i.name,
           t.date,
           t.qty_change,
           t.purpose
    FROM   Transactions t
    JOIN   Items i ON t.item_id = i.item_id
    ORDER  BY t.trans_id DESC

  FOREIGN KEY CONSTRAINT:
    CONSTRAINT fk_item
        FOREIGN KEY (item_id)
        REFERENCES Items(item_id)
        ON DELETE CASCADE

  REAL-WORLD SIGNIFICANCE:
    • Prevents orphan records: You cannot add a transaction for an
      item_id that does not exist in Items.
    • ON DELETE CASCADE: If an item is deleted from Items, all its
      historical transaction logs are automatically deleted too,
      preventing dangling pointers and database corruption.

  PART J — CONTINUOUS LOOP & INPUT VALIDATION (terminal_app.py)
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

  1. THE UNBROKEN while True LOOP:
     • The main menu in terminal_app.py runs inside an unbroken `while True:` loop.
     • The program displays options (1 to 7) and executes the chosen feature.
     • It ONLY terminates when the user explicitly chooses Option 7 (`break`).
     • If an invalid choice is entered, it prints a message and loops back.

  2. THE PAUSE MECHANISM:
     • After every operation completes (or returns an error), the program calls:
       input("\nPress Enter to return to menu...")
     • Why? Without this pause, the terminal would immediately reprint the
       menu and the user would never have time to read the confirmation
       message or query results.

  3. NUMERIC INPUT VALIDATION (try/except ValueError):
     • In beginner programs, typing a letter like "abc" when prompted for an
       ID or quantity causes Python to crash with `ValueError: invalid literal for int()`.
     • We wrap all numeric inputs in `try/except ValueError`:
         try:
             qty = int(qty_input)
         except ValueError:
             print("Error: Quantity must be a valid whole number.")
             return
     • If the user types a letter, the error is caught gracefully, an
       informative message is displayed, and the program returns to the
       menu instead of crashing.

  4. CROSS-PLATFORM SCREEN CLEARING:
     • Windows uses the shell command `cls`.
     • Linux / macOS uses the shell command `clear`.
     • Our clear_screen() checks `os.name`:
         cmd = "cls" if os.name == "nt" else "clear"
         os.system(cmd)

  PART K — TKINTER DESKTOP GUI ARCHITECTURE (gui_app.py)
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

  1. PURELY PROCEDURAL GUI:
     • Standard GUI tutorials use Object-Oriented Programming (classes, self).
     • However, CBSE Class 12 CS guidelines prioritize procedural programming.
     • gui_app.py is 100% procedural: it uses functions that accept widget
       references as parameters and bind callbacks.

  2. THE EVENT LOOP (root.mainloop()):
     • In terminal programs, Python executes line by line sequentially.
     • In GUI programs, `root.mainloop()` turns control over to tkinter's
       event loop. It continuously listens for mouse clicks, keyboard presses,
       and window resize events, dispatching callbacks accordingly.

  3. WIDGETS USED IN gui_app.py:
     • tk.Tk()        : The root application window.
     • tk.Label       : Static text labels and header banners.
     • tk.Entry       : Single-line text input fields.
     • tk.Button      : Clickable push buttons styled with distinct colors.
     • tk.LabelFrame  : Bordered grouping boxes with titles (e.g. "Add Item").
     • ttk.Notebook   : Multi-tab container widget (Manage, Inventory, Logs).
     • ttk.Treeview   : Spreadsheet-like table widget with columns and headers.
     • ttk.Scrollbar  : Vertical scrollbar attached to the Treeview.
     • messagebox     : System popup dialogs (.showinfo(), .showerror()).

  PART L — TKINTER EVENT CALLBACKS & lambda:
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

  HOW A BUTTON CLICK EXECUTES SQL:
    1. The user enters data into Entry fields and clicks "➕ Save New Item".
    2. Tkinter fires the button's `command=` function.
    3. The callback extracts text using `entry.get()`.
    4. Input validation checks if fields are non-empty and valid numbers.
    5. The callback calls db_add_item(name, qty), which sends SQL to MySQL.
    6. On success, `messagebox.showinfo()` shows a confirmation alert.
    7. `entry.delete(0, tk.END)` clears the input fields for the next entry.
    8. `refresh_inventory(tree)` queries MySQL and reloads the table.

  WHY IS lambda: MANDATORY ON BUTTONS?
    • A button's `command=` parameter expects a reference to a function
      that takes ZERO arguments.
    • If we write:
        command = action_add_item(entry_name, entry_qty, tree)
      Python calls action_add_item IMMEDIATELY at startup when building
      the window, instead of waiting for the user to click the button!
    • By writing:
        command = lambda: action_add_item(entry_name, entry_qty, tree)
      `lambda:` creates an anonymous zero-argument function that runs
      ONLY when clicked, passing the widget references at click time.

  PART M — ttk.Treeview : TABLE POPULATION & LIVE REFRESHES
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

  HOW DATA GETS INTO THE TREEVIEW:
    1. db_fetch_inventory() runs a SELECT query in MySQL.
    2. cursor.fetchall() returns a list of tuples:
       [(1, "Beaker 250ml", 50), (2, "Test Tube", 120)]
    3. load_treeview() iterates through this list:
       tree.insert("", tk.END, values=row)
       This inserts each tuple as a visible table row.

  HOW LIVE REFRESHES WORK:
    • A Treeview does not automatically sync with MySQL.
    • After every Add, Issue, or Restock operation, refresh_inventory()
      is called:
        a) Clears old rows: for child in tree.get_children(): tree.delete(child)
        b) Re-queries MySQL for the latest data.
        c) Inserts the fresh rows into the Treeview.
    • This gives the user an instantaneous real-time spreadsheet view.

  CROSS-PLATFORM MOUSE WHEEL SCROLLING:
    • Linux X11 uses mouse button events: `<Button-4>` (up) and `<Button-5>` (down).
    • Windows uses `<MouseWheel>` with `event.delta`.
    • Our bind_cross_platform_scroll() binds BOTH event types so scrolling
      works smoothly on any operating system.

  === CATEGORY 1: DATABASE & SQL ===

  Q1: What is mysql-connector-python?
  A1: It is the official Python library that implements the Python DB-API
      to establish a TCP or socket connection between Python scripts and
      the MySQL / MariaDB database server.

  Q2: What is the difference between conn and cursor?
  A2: conn represents the physical communication channel (socket/TCP) to the
      database server. cursor is a Python control object created within that
      connection used to execute SQL queries and fetch results.

  Q3: What is the difference between cursor.execute() and conn.commit()?
  A3: execute() submits SQL queries to the database server but holds changes
      in an active transaction buffer. commit() permanently flushes and
      saves those changes to disk storage.

  Q4: When is conn.commit() required, and when is it not?
  A4: commit() is mandatory for Data Manipulation Language (DML) queries that
      modify data (INSERT, UPDATE, DELETE). It is NOT required for SELECT
      queries since reading data does not alter the database.

  Q5: What is the difference between fetchone() and fetchall()?
  A5: fetchone() retrieves only the next single row from the cursor buffer as
      a tuple (or None if no rows remain). fetchall() retrieves all remaining
      rows as a list of tuples.

  Q6: Why use %s parameterized placeholders instead of string concatenation?
  A6: %s separates SQL commands from user-supplied data. The driver automatically
      escapes dangerous characters, completely preventing SQL Injection attacks.

  Q7: What does AUTO_INCREMENT do in the Items table?
  A7: It instructs MySQL to automatically assign a sequential, unique integer
      (1, 2, 3...) to item_id for each new row inserted, guaranteeing unique
      Primary Keys without manual calculation.

  Q8: What is a Foreign Key constraint?
  A8: A relational rule enforcing referential integrity between two tables.
      In our project, Transactions.item_id references Items.item_id, preventing
      transaction records from being linked to non-existent items.

  Q9: What does ON DELETE CASCADE mean?
  A9: If a parent row in the Items table is deleted, MySQL automatically deletes
      all corresponding child rows in the Transactions table, preventing orphan
      records.

  Q10: What is an INNER JOIN?
  A10: A SQL clause that combines rows from two tables based on a related
       column. We join Transactions and Items on item_id to display the item's
       name alongside transaction details.

  === CATEGORY 2: CONFIGURATION & CROSS-PLATFORM ===

  Q11: Why is database configuration kept in db_config.py?
  A11: To centralize connection parameters (host, user, password, port) in a
       single file. Changes only need to be made once, making the codebase
       maintainable and portable.

  Q12: How does initialize_database() prevent startup crashes?
  A12: It connects to the MySQL server and executes CREATE DATABASE IF NOT EXISTS
       and CREATE TABLE IF NOT EXISTS. On a new machine, the entire database
       and table schema are created automatically without manual SQL imports.

  Q13: How does the app achieve cross-platform compatibility?
  A13: By checking os.name (e.g. 'cls' on Windows vs 'clear' on Linux), avoiding
       hardcoded file paths, and supporting both TCP port 3306 (Windows) and
       local unix_socket authentication (Linux MariaDB) automatically.

  Q14: Where do you change the MySQL password if required?
  A14: Inside the DB_CONFIG dictionary in db_config.py:
       DB_CONFIG = {"host": "localhost", "user": "root", "password": "your_password"}

  === CATEGORY 3: TERMINAL APP & ERROR HANDLING ===

  Q15: Why is terminal_app.py structured inside a while True loop?
  A15: To provide a continuous menu interface that stays active after performing
       actions. It only exits when the user explicitly chooses Option 7.

  Q16: Why is input("\nPress Enter to return to menu...") used?
  A16: It pauses execution so the user can inspect output tables or confirmation
       messages before the screen is cleared and the menu re-displays.

  Q17: Why do we wrap int(input(...)) in a try/except ValueError block?
  A17: If a user enters letters or symbols when a number is expected, int() raises
       a ValueError. The try/except block catches this exception, prints a friendly
       error, and returns to the menu safely instead of crashing the program.

  Q18: What is database Atomicity and where is it used?
  A18: Atomicity ensures that a group of operations all succeed together or all
       fail together. In issue_item(), both the stock UPDATE and the transaction
       INSERT are committed together with a single conn.commit().

  === CATEGORY 4: TKINTER GUI ===

  Q19: What is the Tkinter event loop (root.mainloop())?
  A19: An infinite background loop that keeps the desktop window visible and
       actively monitors user events like mouse clicks and keystrokes.

  Q20: What is ttk and how does it differ from tk?
  A20: tk provides basic GUI widgets. ttk ("themed Tk") provides modern,
       styled widgets such as ttk.Treeview (tables) and ttk.Notebook (tabs).

  Q21: Why do we use lambda: when assigning button commands?
  A21: Tkinter's command= parameter expects a callable with zero arguments.
       lambda: creates an anonymous zero-argument function that delays execution
       until the button is clicked, allowing us to pass widget references.

  Q22: How does entry.get() and entry.delete() work?
  A22: entry.get() reads the current text string from an Entry box.
       entry.delete(0, tk.END) clears all characters from index 0 to the end.

  Q23: How does ttk.Treeview display database records?
  A23: Treeview organizes data into columns. We clear existing rows using
       tree.delete() and insert rows fetched from MySQL using
       tree.insert("", tk.END, values=row_tuple).

  Q24: How does the Low Stock Alert work in the GUI?
  A24: The user enters a threshold number. The GUI executes a SELECT query with
       `WHERE total_qty <= %s` and repopulates the Treeview with only matching items.

  Q25: Does this project use any Object-Oriented Programming (OOP)?
  A25: No. It is 100% procedural, using only functions, conditional statements,
       loops, lists, and tuples, strictly adhering to CBSE Class 12 CS guidelines.
